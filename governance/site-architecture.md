# GitHub Pages 首页信息架构与分类体系

## 产品定位

Timeline Events 是一个可追溯、可访问、可搜索的**事件编年资料库**，而不是新闻滚动站，也不是在浏览器里虚假显示“AI 正在生成”的静态模型演示。站点优先提供真实存在的文章、来源说明和可复用的研究 SKILL。

## 首页结构（已实现）

1. **品牌导航**：Logo / 事件库 / 分类 / 研究标准 / 创作入口 / GitHub。
2. **Hero 主张**：一句价值陈述、两条 CTA、实有主题数量、节点数量和输出格式。
3. **可理解的视觉示意**：用 CSS 时间轴展示上/下事件、转折、证据和阶段。
4. **事件目录**：搜索框、一级分类筛选、实际条目卡（状态、节点数、时间跨度、真实页面链接）。
5. **知识分类**：6 个一级类，4 个示范二级标签/类，显示真实已发布数量。
6. **证据工作流**：界定范围 → 来源核验 → 结构建模 → 排版渲染 → 质量审查。
7. **创作入口**：主题 / 时间范围 / 输出格式 / 研究重点 → 可复制 Agent 指令。*不会宣称静态站点直接调用模型*。
8. **页尾**：使用入口、项目源码、两份 SKILL 与 AGENTS.md。

这些是**主题分类**；横跨多个领域的事件只选择一个主分类，其他维度放入 `tags`，避免一个事件在首页被重复计数。

## 事件状态模型

- `reference_transcription`：用户图像等来源的版式转录，**未独立核验**；卡片橙色小标签，正文下方有免责声明。可用于版式展示，但不可加入“事实确认”统计。
- `verified`：已有逐节点来源映射、事实交叉审查和发布记录。程序只能验证 URL、结构和引用关联；**编辑或研究 Agent 必须实际阅读原始资料**才可给此状态。
- 将来如加入 `draft`/`disputed`，必须先扩展 schema、UI、过滤和测试，不能静默推断。

## 数据与渲染

- 目录：`docs/data/catalog.json`，维护 `taxonomies[]` 和 `events[]` 两个数组。
- 文章：`docs/events/<slug>/index.html`。卡片 URL 应使用 `./events/<slug>/`，适配 GitHub Pages 项目站点的子路径。
- `nodes` 只由实际文章记录的节点数量决定；首页统计为实际收录的 event 数，不包含分类规划或草稿。
- 前端脚本只读取仓库内的静态 JSON，使用 `textContent` 创建条目，避免用户提供的描述产生 HTML 注入。
- 首页保持可离线构建。生成提示词动作仅使用浏览器复制能力，无需 API key；研究与生成在具备研究工具的 Agent 环境中执行。

## 未来阶段（尚未实现）

- “按年份/国家/主角交叉筛选”：新增标签维度和检索索引后再启用。
- “内容质量评分/争议标签”：需要数据模型与可复核规则，不在首页凭空打分。
- “全文搜索/时间区间缩略图/订阅”：需完善数据数量、静态搜索索引或自动化才有意义。
- “浏览器一键生成 HTML”：需要后台服务、API key 安全代理、限流与任务生命周期；静态 Pages 不具备此能力，不能误导用户。
